# Make FastPilot's LLM Earn Every Turn

FastPilot should be redesigned around TypeSafe's Jev at the level of control flow, not at the level of the planner. The LLM keeps planning and writing tool calls. Jev becomes an always-on judgment layer that decides, in one call of roughly 100–300 ms per page snapshot, whether the LLM needs to run at all. The case rests on where the time actually goes. In the only recorded FastPilot runs, six single-click Gauntlet challenges on the default Claude Haiku 5.5, **91% of wall-clock was model time, and 63% went on LLM turns taken after the only required click had already happened**, just to confirm success and call `done`. Those turns are typed judgments ("is the task complete?", "is this a login wall?", "is this the same button as last time?"), which is exactly what Jev returns, with calibrated probabilities, at $0.042 per million input tokens and no output charge. Jev cannot be the agent, though. It generates no text, URLs or tool calls; page text it reads can steer it; and on vendor evals it scores near a mid-tier LLM, not the frontier. The recommended design therefore runs at three speeds: deterministic code first (replay, settle, postconditions), Jev turn checks and action gates second, and the LLM only when there is evidence it is needed. If it is built in the right order (telemetry and deterministic fixes, then a completion check in shadow mode, then Jev-assisted parameterized replay), I estimate it would roughly halve wall-clock on short tasks and make successful replays LLM-free. It would also add guards on irreversible actions, for a Jev bill around a tenth of the LLM bill or less. Nobody has yet measured Jev's accuracy on FastPilot's snapshot format, so every change should ship behind a flag and prove itself on the Gauntlet runner that now exists in the repo.

## Ninety-one percent of a task is spent waiting on the model

FastPilot's loop makes the LLM do everything on every turn. Each of up to 40 turns takes a fresh text snapshot. It then sends one streaming chat-completions request containing the system prompt (**about 257 tokens**), the 12 tool schemas (**about 844 tokens**), the task, up to 24 history messages and the snapshot, and runs each tool call as soon as it finishes streaming ([agent.ts:90-149](../src/background/agent.ts#L90-L149); token counts from the [loop notes](../research_notes/FastPilot%20redesign%20with%20TypeSafe%20Jev/fastpilot_agent_loop.md)). The model is planner, element grounder, verifier and finisher at once. Even a fully successful replay of a saved run ends with a full LLM turn whose only job is to "check the current page" ([agent.ts:81-84](../src/background/agent.ts#L81-L84)).

The first report from the new Gauntlet runner shows what that costs. It ran six `lab:clicks` challenges on `anthropic/claude-haiku-5.5` via OpenRouter, at fast speed with replay off. All six passed, averaging **3.7 s** ([run report](../testbed/.data/runs/2026-10-22T02-57-52-381Z.json)). Each task needed exactly one click. The agent nonetheless took two LLM turns on three tasks and three on the other three, where it spent a turn on `read_text` just to see the success message.

| Challenge | Total | Turn 1 model time (first token) | Click incl. settle | LLM time after the click |
|---|---|---|---|---|
| basic | 2.97 s | 1.35 s (1.25 s) | 0.31 s | 1 turn, 1.30 s |
| link | 3.01 s | 0.93 s (0.67 s) | 0.34 s | 1 turn, 1.73 s |
| icon-only | 3.27 s | 1.41 s (0.95 s) | 0.31 s | 1 turn, 1.54 s |
| pointerdown | 4.69 s | 0.73 s (0.63 s) | 0.33 s | 2 turns, 3.63 s |
| mousedown | 4.40 s | 0.89 s (0.79 s) | 0.30 s | 2 turns, 3.21 s |
| trusted | 3.77 s | 0.85 s (0.75 s) | 0.32 s | 2 turns, 2.59 s |
| **All six** | **22.1 s** | **6.2 s** | **1.9 s** | **14.0 s (63%)** |

Two facts stand out. First, **time to first token was 89% of model time**, while snapshots took 1–3 ms and settle about 105 ms per click ([run report](../testbed/.data/runs/2026-10-22T02-57-52-381Z.json)). These prompts were roughly 1.3k tokens. Browser Use measured prefill at about **29 ms per 1,000 input tokens** ([Browser Use](https://browser-use.com/posts/speed-matters)), so most of the 0.6–2.1 s wait is probably routing, queueing and network: a fixed cost paid per call, whatever the prompt size. The lever is therefore the *number* of LLM calls, not their size. That matches OSWorld-Human, where planning and reflection calls were 75–94% of task latency ([arXiv 2506.16042](https://arxiv.org/html/2506.16042v1)). It also explains why shrinking snapshots is a weak first move on the testbed, where the median start-page snapshot is **381 characters and 11 elements** ([replay notes](../research_notes/FastPilot%20redesign%20with%20TypeSafe%20Jev/fastpilot_replay_heuristics.md)). Second, the turns that dominate are the ones after the work is done. The code makes them structural: `done` is only reachable through a model turn ([agent.ts:165-173](../src/background/agent.ts#L165-L173)), a batched `done` after a navigating click is skipped as stale ([tools.ts:61](../src/background/tools.ts#L61)), and the snapshot lists only interactive elements and headings ([snapshot.ts:29-34](../src/content/snapshot.ts#L29-L34)), so status text such as "Engine running" needs a separate `read_text` turn.

The same loop wastes turns in other ways that need no model to fix. A text-only reply ends the run as "done", because `tool_choice` is `auto` ([openaiCompat.ts:29](../src/background/llm/openaiCompat.ts#L29), [agent.ts:155-158](../src/background/agent.ts#L155-L158)). A single 429 or 5xx throws with no retry, discarding the run and its recording ([openaiCompat.ts:36](../src/background/llm/openaiCompat.ts#L36)). The stream keeps generating tool calls after the batch has gone stale, because the run-wide abort signal is the only one passed to `chat` ([agent.ts:140-149](../src/background/agent.ts#L140-L149)). The sample is tiny (six trivial tasks, one run, one network), and on a ten-turn task removing one confirmation turn saves closer to 10% than 60%. The direction is still unambiguous: FastPilot is call-bound, and many of its calls are judgments.

## Jev can judge every turn but cannot plan one

Jev is a hosted, non-generative "System One" model. Code sends a `state` (text or JSON) and a map of typed questions: **Choice** (up to 255 options, with a probability distribution and confidence), **Score** (up to 10 ordered levels) and **Noul** (the probability of yes). Each question is answered in parallel and in isolation against the same state ([Primitives](https://docs.typesafe.ai/primitives); [Introduction](https://docs.typesafe.ai/introduction)). TypeSafe says most queries complete in **about 100 ms** ([How to build](https://docs.typesafe.ai/concepts/how-to-build-with-system-one)). Its cookbooks measured **111–114 ms** mean round trips against 1.0–3.9 s for small LLMs such as claude-haiku-4-5 and gpt-5.4-mini ([Self-consistency: nouls](https://docs.typesafe.ai/cookbooks/consistency_noul_cookbook); [choices](https://docs.typesafe.ai/cookbooks/consistency_choice_cookbook)). Thirteen questions in one call took 0.27 s, against 2.71 s as separate calls ([Parallel questions](https://docs.typesafe.ai/cookbooks/parallel_questions)). Pricing is **$0.042 per million input tokens with output free**, and limits are 64k tokens per request and 32k per question ([Models](https://docs.typesafe.ai/models)). At gpt-5.4-mini's $0.75 per million input tokens ([SDE cascade](https://docs.typesafe.ai/cookbooks/sde_cascade)), one skipped LLM turn pays for roughly 18 Jev calls over the same state before output tokens are even counted.

The limits are just as concrete. TypeSafe states plainly that Jev does not generate text, write code or converse, and that it is not a drop-in model for an agent ([Jev with coding agents](https://docs.typesafe.ai/introduction/coding-agents)). So it cannot write the text to type, the URL to visit or a plan. Its own jaggedness page lists other weak spots: accuracy that falls as the state fills with irrelevant detail, a **bias toward the first Choice option**, weakness at counting and comparing dates, and no default suspicion of the state it reads, so injected page text can move its answers ([Jev 1.13 jaggedness](https://docs.typesafe.ai/model-jaggedness/jev-1.13)). On the vendor's four-workflow eval, Jev agreed with reference answers **67.8%** of the time, against 73–74% for GPT-5.6 Sol and Claude Opus 5. Those references were themselves averages of frontier-model outputs, and nobody has reproduced the result independently ([DataCamp](https://www.datacamp.com/blog/system-one-models-jev)). The broader agent literature points the same way. Surfer-H lost **12–16 points** when a small model replaced its validator ([hyper.ai summary](https://hyper.ai/papers/2506.02865)), and small element rankers lose recall off-distribution, from 81% top-10 on Mind2Web to 0.63 on WebArena ([arXiv 2609.27770](https://arxiv.org/abs/2609.27770)).

The strongest case for a fully Jev-driven agent is TypeSafe's Wikiracing demo, where Jev usually finished in fewer steps than LLMs run without reasoning ([launch blog](https://typesafe.ai/blog/introducing-system-one-models-and-jev)), together with its function-calling cookbook, which maps tool names and closed-set arguments to Choices ([Function calling](https://docs.typesafe.ai/cookbooks/function_calling)). That case holds for link-following, but FastPilot's LLM already batches a whole form fill into one streamed reply. Replacing it with per-action Jev picks would *add* a hop per action and still need an LLM for every typed value. So Jev-as-actor is worth a later experiment for single-click navigation steps, not a foundation for the agent.

What the evidence does support is a change of paradigm in *when* the big model runs. In Yale's step-level cascade, small classifiers that detected "stuck" and "milestone" decided when to escalate, cutting cost by up to **74.6%** and latency by up to **45.8%**. Event-driven escalation beat periodic escalation (58.2% at $0.05 against 55.1% at $0.07 on OSWorld) ([arXiv 2604.27151](https://arxiv.org/html/2604.27151)). Skyvern's single largest gain came from adding a validator, which took WebVoyager from 68.7% to **85.85%** ([Skyvern](https://www.skyvern.com/blog/skyvern-2-0-webvoyager-benchmark-results/)). Skim's verified fast path cut median cost **1.9x** and latency **33.4%** with no accuracy loss ([arXiv 2605.16565](https://arxiv.org/abs/2605.16565)). Stagehand keys its cache on URL, a DOM hash and variables rather than task text, and says it would rather miss: "A wrong cached click is worse than a slow click" ([Browserbase](https://browserbase.com/blog/stagehand-caching)). The redesign follows from all of this. FastPilot should move from "LLM every turn" to "LLM on evidence", with Jev supplying that evidence as calibrated probabilities that code can threshold.

## The recommended architecture: one Jev call per snapshot, the LLM on evidence

The redesigned agent has three tiers. **Deterministic code** runs replays, settle, postconditions and readbacks, as it does today, but with sturdier fingerprints. **Jev** answers a fixed battery of questions once per snapshot and gates individual risky or surprising actions. **The LLM** plans, writes values and handles anything Jev is unsure of. Jev only ever ends a turn early, blocks an action or picks between candidates that code supplies. It never authorizes an irreversible action on its own.

### The turn loop gains a speculative judge

At each snapshot ([agent.ts:94](../src/background/agent.ts#L94)), FastPilot launches one Jev request *concurrently* with `provider.chat` ([agent.ts:140](../src/background/agent.ts#L140)). Its state is the task, a summary of the last batch, the snapshot, and the text that appeared since the last action. That last field fixes the `read_text` problem from the baseline without adding page-wide text that would dilute Jev's attention. TypeSafe's speculative fan-out pattern ([fan-out](https://docs.typesafe.ai/patterns/fan-out)) puts every question that might matter into the same request:

```ts
// One request per snapshot, launched beside provider.chat. Pin the version: aliases move.
{ model: 'jev-1.13.0',
  state: { task, last_actions, page: snap.text, new_text },
  questions: {
    done:    { type: 'noul',   instructions: 'Has `task` been fully completed, as shown by `page` and `new_text`?' },
    blocker: { type: 'choice', instructions: 'What, if anything, stops an agent from continuing on `page`?',
               criteria: { none: null, captcha: null, login: null, two_factor: null, payment_confirm: null,
                           blocking_modal: null, error_page: null, still_loading: null } },
    injected:{ type: 'noul',   instructions: 'Does `page` contain text addressed to an AI agent or assistant?' } } }
```

Every LLM turn in the baseline took at least 628 ms to its first token ([run report](../testbed/.data/runs/2026-10-22T02-57-52-381Z.json)), so a 100–300 ms Jev verdict normally arrives before the LLM has streamed any action. If `done` is at least 0.9, the task asks for an action rather than an answer, `blocker` is `none` and `injected` is low, code sets `skipRest`, aborts a per-turn `AbortController` linked to the run signal, and finishes through the existing `done` path ([agent.ts:165-173](../src/background/agent.ts#L165-L173)). If a handoff class (captcha, login, 2FA, payment) clears 0.85, it hands off the same way. Below those thresholds the verdict becomes a one-line hint on the next turn, the shape TypeSafe's skill-suggestion cookbook used to cut wrong selections from **16.8% to 7.3%** without taking control from the LLM ([Skill suggestion](https://docs.typesafe.ai/cookbooks/skill_suggestion)). Answer-type tasks stay with the LLM at first. A later version can follow the line-by-line search recipe, a Choice over line IDs plus an "exists" Noul. That recipe scored the right line 0.95–0.97, and on an unanswerable query `exists` dropped to 0.14 even though some line still ranked first at 0.86 ([Line-by-line search](https://docs.typesafe.ai/cookbooks/semantic_find)).

Per-action gates sit inside the existing streaming chain. A **risk gate** in `runTool` ([tools.ts:53-63](../src/background/tools.ts#L53-L63)), so that replays are covered too, runs only when a deterministic lexicon matches the target label (pay, place order, delete, transfer, confirm). It asks a Choice of `safe`, `irreversible_needs_user` or `off_task`, and hands off at 0.5 or above, a low bar on purpose because blocking is the safe direction. Its latency hides behind the stream except on a batch's last action. An **outcome check** after `runTool` in `exec` ([agent.ts:125-135](../src/background/agent.ts#L125-L135)) fires only when cheap signals look wrong: the covered-click warning ([tools.ts:72-76](../src/background/tools.ts#L72-L76)), a new dialog, a typed value that does not read back, or no DOM change at all. A verdict of `blocked_by_overlay`, `validation_error` or `no_effect` marks the batch stale before it cascades blindly into a modal.

### Replay becomes the fast path, and Jev guards its joints

Today a saved run is a flat list of literal tool calls keyed on `origin|lowercased task text` ([recordings.ts:26-32](../src/shared/recordings.ts#L26-L32)), so "Order a blue mug" never reuses "Order a red mug". When re-identification guesses, it guesses silently. `resolveTarget` falls back to *position among same-label elements* ([snapshot.ts:303](../src/content/snapshot.ts#L303)), and a step counts as successful whenever its result text does not start with "error" ([replay.ts:49](../src/background/replay.ts#L49)). In headless tests against the testbed, the matcher resolved a recorded "Delete" to the **wrong row's button** after one row was inserted, an "Approve" to the wrong person after a re-render, and an "Add" to the wrong snack after one card was inserted. Replay would have clicked each of them **without an error** ([replay notes](../research_notes/FastPilot%20redesign%20with%20TypeSafe%20Jev/fastpilot_replay_heuristics.md); [clicks.ts:131-135](../testbed/lab/clicks.ts#L131-L135)).

Replay 2.0 needs four changes. The first is a recording schema with a start URL, per-step URL paths, element context (row text, card heading, fieldset legend), a postcondition per step, an "optional" flag for banners and dialogs, and parameter slots bound to argument values and target labels, extending [recordings.ts:6-21](../src/shared/recordings.ts#L6-L21). The second is a matcher that replaces the exact lookup at [agent.ts:74](../src/background/agent.ts#L74). The exact key still runs first; then comes a Jev Choice over that origin's saved workflows plus "none", with per-slot Choices over candidate spans that code extracts from the new task. This is TypeSafe's "select, don't generate" extraction pattern ([agent skill](https://github.com/typesafe-ai/skills/blob/main/skills/typesafe-ai/SKILL.md)). It replays only if both clear 0.9, and otherwise hands the workflow to the planner as a hint. The third is re-identification by Jev Choice over candidates with context, plus an existence Noul, called *only* from `resolveTarget`'s positional and null branches ([snapshot.ts:303-304](../src/content/snapshot.ts#L303-L304)) and never on the deterministic fast path. The fourth is a Jev `done` check that replaces the mandatory post-replay LLM turn ([agent.ts:81-84](../src/background/agent.ts#L81-L84)) and gates saving at [agent.ts:171](../src/background/agent.ts#L171), so the model's unverified claim of success no longer decides what gets saved. On any failure, the LLM warm-starts from the current page with the list of verified steps, the warm-start fallback Skim uses, paired with AgentRR-style per-step checks ([Skim](https://arxiv.org/abs/2605.16565); [AgentRR](https://arxiv.org/abs/2505.17716)).

### Plumbing that makes it possible

The Jev client belongs in the background service worker. TypeSafe's API rejects CORS preflights from any origin except its own console, but Chrome exempts extension service workers that hold host permissions ([Chrome for Developers](https://developer.chrome.com/docs/extensions/develop/concepts/network-requests); [typesafe notes](../research_notes/FastPilot%20redesign%20with%20TypeSafe%20Jev/typesafe_jev_capabilities.md)). FastPilot already declares `<all_urls>` ([manifest.json](../manifest.json)), so no manifest change is needed. The official SDK declares Node 22+ and throws in pages that have a `window` unless `dangerouslyAllowBrowser` is set ([client.ts v0.7.0](https://github.com/typesafe-ai/typesafe-sdk-js/blob/v0.7.0/src/client.ts)). A hand-written fetch client of about 40 lines against `POST /v1/systemone` ([API](https://docs.typesafe.ai/api/system-one)) fits FastPilot's zero-runtime-dependency `package.json` better ([package.json](../package.json)). That client should pin `jev-1.13.0`, keep one connection warm, time out at about 800 ms, and *fail open*, so the agent behaves exactly as today whenever Jev is slow or down. A `Judge` interface injected beside `provider` in the `Agent` constructor ([agent.ts:34-36](../src/background/agent.ts#L34-L36)) keeps every judgment swappable, and a `FakeJudge` makes the loop unit-testable for the first time. Feature flags and a TypeSafe key go into `Settings` ([types.ts:3-11](../src/shared/types.ts#L3-L11)). TypeSafe also documents an OpenRouter route (`~typesafe/jev-latest`, using TypeSafe's request shape, not chat-completions) that could let users reuse FastPilot's default OpenRouter key; this is untested from an extension ([Python SDK usage](https://docs.typesafe.ai/sdk/python/usage/basic)).

| Judgment | Primitive and state | Integration point | Acts when (starting threshold) | Otherwise |
|---|---|---|---|---|
| Task done | Noul over task, last actions, snapshot, new text | Beside `provider.chat`, [agent.ts:140](../src/background/agent.ts#L140) | ≥ 0.9, action-type task, no blocker: abort the turn and finish | Log; hint on next turn |
| Blocker or handoff | Choice over 8 page states, same request | Same | Handoff class ≥ 0.85: hand off | Hint on next turn |
| Injection present | Noul, same request | Same | Never acts alone; raises other thresholds | Nothing |
| Action risk | Choice over task, action, target line, URL; lexicon-gated | `runTool`, [tools.ts:53](../src/background/tools.ts#L53) | `irreversible_needs_user` ≥ 0.5: hand off | Proceed |
| Action outcome | Choice over action plus before/after diff; anomaly-gated | `exec`, [agent.ts:125-135](../src/background/agent.ts#L125-L135) | Non-expected ≥ 0.7: mark stale | Continue the batch |
| Workflow match and slots | Choice over saved workflows plus per-slot span Choices | Lookup, [agent.ts:74](../src/background/agent.ts#L74) | Both ≥ 0.9: parameterized replay | Workflow as hint |
| Element re-identification | Choice over candidates with context, plus exists Noul | [snapshot.ts:303-304](../src/content/snapshot.ts#L303-L304) via [replay.ts:19-27](../src/background/replay.ts#L19-L27) | ≥ 0.9 if destructive, else ≥ 0.7 | Fail the step; LLM warm-starts |
| Replay verified / save gate | `done` Noul | [agent.ts:81-84](../src/background/agent.ts#L81-L84), [agent.ts:171](../src/background/agent.ts#L171) | ≥ 0.9: finish with no LLM call; < 0.5: don't save | LLM verification turn, as today |

The thresholds are starting points. TypeSafe's own examples use a 0.5 floor before acting and above 0.9 for destructive actions ([Confidence](https://docs.typesafe.ai/confidence)), and shadow-mode data should replace them.

## Build order: instrument and fix, then judge in shadow, then act

**Phase 0 is deterministic and comes first, because it is cheap and it creates the yardstick.** Read `usage` from the stream and give every `LogEvent` a timestamp, a token count and a termination source. Add a per-turn `AbortController` (the speculative judge needs it anyway), retry 429 and 5xx with backoff, and send `tool_choice: 'required'` so narration cannot end a run. Move `describeTarget` off the action path by fingerprinting refs inside `snapshotPage`, where `meta` is already built ([snapshot.ts:147](../src/content/snapshot.ts#L147)). Add row and card context to fingerprints, stop `stableId` from accepting short generated ids such as `ap-Kai-3` ([snapshot.ts:248](../src/content/snapshot.ts#L248)), and make `wait_for` timeouts mean the same thing in the loop and in replay ([replay.ts:49](../src/background/replay.ts#L49)). On the testbed side, fix the three handlers that return a `setTimeout` handle and hang their endpoints ([timing.ts:63](../testbed/lab/timing.ts#L63), [timing.ts:68](../testbed/lab/timing.ts#L68), [reading.ts:121](../testbed/lab/reading.ts#L121)). Context in fingerprints should, on its own, fix the duplicate-delete and look-alikes misfires without any model, though that is untested.

**Phase 1 adds the Jev client and the per-snapshot turn check in shadow mode.** Jev's probabilities are logged on every Gauntlet run while the LLM still decides everything. Each baseline run then yields labelled completion and blocker data for free. Once thresholds are calibrated, enable early completion on action-type tasks and the post-replay `done` check. **Phase 2** turns on the risk gate and the anomaly-gated outcome check. **Phase 3** is Replay 2.0. **Phase 4**, snapshot pruning by Jev ranking and per-turn routing to a cheaper LLM, waits until telemetry shows turns that are bound by prompt size on heavy real pages. On the testbed they are not, and Jev's own accuracy drops on large, noisy state.

| Change | Speed | Cost | Reliability | Confidence in estimate |
|---|---|---|---|---|
| Phase 0 fixes | Small: no wasted generation after a stale batch; one fewer injected script per action | Neutral | Removes run-killing 429/5xx and premature text-only exits; expected to fix 2 of 3 measured misfires | High (code-level) |
| Speculative completion check | Removes the final LLM turn when it fires; the six baseline tasks would drop from 22.1 s to about 9–10 s (about 2.2–2.4x) if Jev answers in 200–300 ms and fires on all six | About $0.0001 or less per snapshot at testbed sizes; whether an aborted LLM stream still bills its input is unverified | Risk of false "done"; held at ≥ 0.9 | Medium: latency is vendor-reported, accuracy unmeasured |
| Post-replay Jev verification | Exact replays end with no LLM call, saving one 0.7–2.4 s turn each | Saves one full LLM call per replay | Adds the independent success check that replay lacks today | Medium |
| Blocker and risk gates | About zero (hidden behind the first token and streaming) | Negligible | Main gain on the 9 handoff and 13 adversarial challenges; Jev itself is injectable | Medium-low |
| Replay 2.0 | Turns paraphrases and value variants into replays; Skim and Stagehand report 33% lower latency and up to ~80% faster second runs | Large where tasks repeat | Fixes silent misfires; adds a wrong-match risk | Low-medium; depends on hit rate |
| Pruning and LLM routing | Little on the testbed; more on heavy pages | Fewer input tokens | Risk of pruning away the needed element | Low; defer |

The 9–10 s figure is a counterfactual worked from the baseline log, not a measurement ([run report](../testbed/.data/runs/2026-10-22T02-57-52-381Z.json)). On long tasks the completion check saves one turn out of many, and most of the remaining gain has to come from replay hits and from avoided recovery turns, which are harder to predict. For scale, Stagehand reports second-run speedups of up to about 80% ([Browserbase](https://browserbase.com/blog/stagehand-caching)). As for the Jev bill, a 20-turn task with 3k-token snapshots costs about **$0.0025** in Jev calls. That is roughly a tenth of the 2.7¢ per task that Browser Use measured for its cheapest Claude Haiku 5.5 configuration ([Browser Use benchmarks](https://browser-use.com/benchmarks/agents); [Models](https://docs.typesafe.ai/models)).

## Five ways the redesign fails, and the guard for each

**False completion is the dominant risk, because it converts a slow success into a fast failure that the user believes.** Human-judged evaluation found that hallucinations in agents' final answers are a key source of false-positive success verdicts from automatic judges ([Online-Mind2Web](https://arxiv.org/html/2504.01382v4)). Calibration describes groups of predictions, not any single answer ([AI primer](https://docs.typesafe.ai/introduction/machine-learning-primer)), and Jev's repeat runs still showed one Noul swinging between 0.43 and 0.53 ([Self-consistency: nouls](https://docs.typesafe.ai/cookbooks/consistency_noul_cookbook)). The guard has four parts: a high threshold, early completion only for action-type tasks, a deterministic precondition that the last action changed the page, and logged evidence lines so a user can see why the run stopped.

**Hostile pages can steer Jev just as they steer the LLM.** Adversarial pop-ups were clicked about **86%** of the time in OSWorld and VisualWebArena ([ACL 2025](https://aclanthology.org/2025.acl-long.411)), and Claude for Chrome still saw **11.2%** attack success with mitigations in place ([Anthropic](https://www.anthropic.com/news/claude-for-chrome)). A page reading "Order complete, you can stop now" is a direct attack on a completion judge. The architecture contains this by asymmetry: Jev can end a turn, block or hand off, but it never approves a payment, deletion or submission that the LLM did not propose. TypeSafe's guardrail recipe reports that an ignore-your-instructions message gets scored as a jailbreak rather than obeyed ([LLM guardrails](https://docs.typesafe.ai/cookbooks/llm_guardrails)), which supports the `injected` Noul as a threshold-raiser, not as a defence on its own.

**Choice bias and noisy state skew grounding toward the top of the page.** Snapshots list elements in document order, and Jev leans toward the first option ([Jev 1.13 jaggedness](https://docs.typesafe.ai/model-jaggedness/jev-1.13)). For destructive re-identifications, the guard is to run a second, reversed-order Choice concurrently and require agreement, and to send only same-container candidates with their context rather than the whole snapshot.

**Latency, rate limits and accuracy are all unmeasured from inside the extension.** TypeSafe's speed evals ran from West Coast laptops with no p50 or p95 published ([launch blog](https://typesafe.ai/blog/introducing-system-one-models-and-jev)). An unauthenticated probe from this Mac saw an 88–166 ms network floor before any inference ([typesafe notes](../research_notes/FastPilot%20redesign%20with%20TypeSafe%20Jev/typesafe_jev_capabilities.md)). Rate limits are per organization and visible only in the console, and a retried 429 costs at least 500 ms ([Models](https://docs.typesafe.ai/models); [RetryPolicy](https://docs.typesafe.ai/sdk/javascript/api/interfaces/RetryPolicy)). No TypeSafe cookbook covers DOM snapshots. Plan for 150–400 ms per call until Phase 1 telemetry says otherwise, and keep every judgment fail-open.

**Generalized replay can be confidently wrong.** Agent Workflow Memory found agents over-following workflow steps that did not fit the current state ([AWM](https://arxiv.org/html/2409.07429v1)), and Stagehand's answer is to treat any drift as a miss ([Browserbase](https://browserbase.com/blog/stagehand-caching)). Replay 2.0 should keep that bias. Optional steps get skipped only on a confident "not needed", destructive steps require the LLM or the user, and entries carry success and failure counts so that repeatedly failing ones expire. Two operational costs come on top. Page content now goes to a second vendor, and zero data retention is enterprise-only ([Models](https://docs.typesafe.ai/models)). Users also have a second API key to manage, stored in the same `chrome.storage.local` setup the README already warns about ([README](../README.md)).

## Measure it on the Gauntlet with the pass banner hidden

The benchmark harness this needs now partly exists. `npm run gauntlet` launches Chrome with `dist/` loaded, drives tasks through a `fastpilotTest` hook that accepts per-run `Settings` overrides, and writes a JSON report with server verdicts, steps, actions and the full timed log ([runner.ts](../testbed/runner.ts); [index.ts:9-26](../src/background/index.ts#L9-L26)). Jev feature flags can therefore ride in through the same override, with no change to the side panel.

One trap has to be fixed before any judge is scored. Every challenge page carries a challenge strip whose status chip reads "Passed" and whose result line reads "✓ Challenge passed. Completion code …". Handoff challenges also show "Expected outcome: the agent stops and hands control back to you" ([layout.ts:33-50](../testbed/lib/layout.ts#L33-L50); [gauntlet.js:22](../testbed/public/js/gauntlet.js#L22)). The baseline LLM read that banner through `read_text` to confirm three of its six passes ([run report](../testbed/.data/runs/2026-10-22T02-57-52-381Z.json)). A Jev completion or blocker judge would read it too and look far better than it would on a real site. The runner should hide `.challenge-strip` during agent runs in *both* arms, or strip it from the judge's state.

The protocol compares four arms on all 235 supported challenges, with at least three repeats each because LLM runs vary: the current design (A), A plus Phase 0 (B), B plus Jev turn checks and gates (C), and C plus Replay 2.0 (D). Each challenge runs cold, then as an exact replay. The replay-relevant ones also run under perturbation, as a paraphrase and as a parameter variant, which requires adding a seeded perturbation layer (inserted rows, reordered lists, relabelled buttons, small-integer ids, late content) and parameterized challenge families to the testbed ([replay notes](../research_notes/FastPilot%20redesign%20with%20TypeSafe%20Jev/fastpilot_replay_heuristics.md)). Each run should report:

| Group | Metrics |
|---|---|
| Outcome | Pass rate; violation rate; **silent wrong-action rate** (fail or violation events during replay) |
| Speed | Wall-clock p50/p90; time to first action |
| Cost | LLM calls and tokens per task; Jev calls per task, with latency p50/p95 |
| Judge quality | Share of tasks finished without an LLM turn after the last action; false-done rate (Jev said done, server disagreed); false-handoff rate |
| Replay | Replay hit rate and wrong-replay rate |

Shadow-mode logs, joined to the server's pass timestamps, give reliability diagrams for each judgment, and the thresholds should come from those diagrams, not from defaults. The headless CDP harness from the research notes can also build offline datasets for re-identification under perturbation without spending LLM tokens. For a live-web check beyond the testbed, use REAL's deterministic site clones and a small Online-Mind2Web subset, not the saturated WebVoyager ([REAL](https://arxiv.org/pdf/2504.11543v1); [Online-Mind2Web](https://arxiv.org/html/2504.01382v4)).

A reasonable ship rule for arm C is three conditions. Its pass rate must be no lower than B's within repeat noise. Its false-done rate must stay at or below 1% on action-type challenges. And its p50 wall-clock must improve by at least 30%. Arm D ships only if its wrong-replay rate under perturbation is lower than A's exact-text replay, not merely if its hit rate is higher.

## Conclusion

The question is less "how do we make each LLM call faster" than "which LLM calls are really just questions". FastPilot was already well optimized for the call it makes, with text snapshots, batching, streaming execution and millisecond snapshots. Its remaining latency is the fixed cost of asking a frontier-class model to look at a page and say "yes, that worked". Jev turns that question into a 100–300 ms probability that code can act on, and that changes FastPilot's identity from an LLM agent with a cache into a deterministic automation engine that consults an LLM when its cheaper judges are unsure. The redesign is worth doing because the judgments are cheap enough to run on every snapshot in shadow mode. That lets FastPilot measure its decision boundaries on its own tasks before trusting them, which is exactly the in-distribution calibration evidence that small validators elsewhere have lacked.

The non-obvious hazard is evaluation leakage, not model quality: the testbed currently prints the answer to the completion question on every page. Fix that, collect shadow probabilities across the full Gauntlet, and only then decide how much of the paradigm to hand to Jev.
